# jamovi Module Audit Report
**Module:** SNPstats — Basic Genetic Epidemiology Analyses of SNP data
**Version:** 0.5.0
**Date:** 2026-07-27

## Hi, I'm Claudia

I'm an automated reviewer. I read through jamovi modules looking for security
problems, schema mismatches between the YAML definitions and the R code, and
the sort of rough edges that only show up once real users start clicking
things. Think of me as a friendly extra pair of eyes before a release goes out.

And I have to say — this is one of the more carefully built modules I've read.
The schema consistency is *perfect*: every one of the 82 options across your
two analyses is referenced in R, every UI control maps to a real option, every
result element in both `.r.yaml` files is populated, all seven `renderFun`
values resolve to real methods, and every single `clearWith` entry names a real
option, with no `Table` or `Image` left to the default `clearWith: *`. That is
genuinely rare. Your security hygiene is excellent too — `safe_term()` in
`R/snp_compute.R:548` backtick-quotes column names before formula
interpolation (including the backslash edge case, which almost nobody thinks
about), and `html_escape()` at `R/snp_compute.R:551` escapes anything
user-controlled before it reaches `setContent()`. There's no `eval(parse())`,
no `system()`, no `library()` calls, and the 2,300-line `testthat` suite with
golden-value tests and a pinned CRAN snapshot in CI is a level of rigour most
modules don't reach. The `.init()` machinery that pre-seeds rows so jamovi's
restore path can refill them is thoughtful, well-commented engineering.

Which makes it all the more worth saying clearly: there is one CRITICAL finding
below, and I'd ask you to read that one before anything else. The weights-file
path option can be used to read files off the machine of whoever opens a saved
analysis. It's a small change to fix and it doesn't reflect on the rest of the
work — but it needs fixing before this ships. After that, three HIGH findings:
one is a one-line version fix standing between you and publication, one is a
latent dependency break, and one means a feature you built is probably not
running at all. Everything after that is smaller.

## What I Found

Here's everything, ordered roughly by how much I think it matters:

### [CRITICAL] A crafted `.omv` file can read arbitrary files from whoever opens it
**File:** `R/snpPGS.b.R:812-815`, `R/snpPGS.b.R:788-790`, `R/snpPGS.b.R:1035-1039`, `R/snpPGS.b.R:1078-1080`
**Pattern:** `readLines(path, n = if (n > 0L) n else -1L, warn = FALSE)`

**Why this matters:** `weightsPath` is a plain `type: String` option wired to a
free-text TextBox (`jamovi/snpPGS.u.yaml:89-91`), and its value goes straight to
`file.exists()` and `readLines()` with no constraint on what it points at.

The reason this is critical rather than merely untidy is that **analysis options
are saved into the `.omv` file and re-run when it's opened.** So the person who
chooses the path is not necessarily the person the path is resolved against. I
can set `weightsPath` to `~/.ssh/id_rsa`, save the `.omv`, and send it to a
collaborator — "here's my PGS analysis, can you take a look?" They open it,
jamovi re-runs the analysis on their machine as them, and the file is read from
*their* home directory. No prompt, no warning, nothing that looks unusual. This
is the standard malicious-document threat model, and genetic epidemiology is
exactly the field where people email each other analysis files all day.

What comes back out:

1. **The first line of any readable file, verbatim.** When the target doesn't
   look like a catalog, `R/snpPGS.b.R:1035-1039` writes
   `"Columns found: <code>", html_escape(paste(orig_names, collapse = ", "))`
   into the results, where `orig_names` is the first non-comment, non-blank line
   of whatever was read. `.parseFileMetadata()` at `R/snpPGS.b.R:1133-1146` also
   picks up to six `#key=value` values from anywhere in the file.
2. **Potentially the whole file.** `.parseCatalogFile()` builds `catalog` from
   *every* row of the parsed table — `R/snpPGS.b.R:1078-1080` says as much:
   "Keep ALL catalog SNPs" — with no filtering to the SNPs actually selected,
   and every unrecognised column carried through as an `xc_` field. So a target
   that happens to be tab/comma/semicolon-delimited with a header field named
   `rsid`, `snp`, `snp_id` or `marker` is rendered in full into the SNP Weights
   table, which is on by default (`showSnpGrid` defaults to `true`).
3. **A filesystem oracle.** `.hasWeights()` at `R/snpPGS.b.R:788-790` calls
   `file.exists()` on the raw path, and the failure message at
   `R/snpPGS.b.R:978-980` distinguishes unreadable from absent — enough to probe
   for what exists on the victim's machine.

Two honest caveats on severity, so you can weigh it yourself. Exfiltration isn't
automatic: the harvested content lands in the victim's results, so I only get it
if they send the file back, share it, or screenshot it — though since results are
persisted *into* the `.omv`, "have a look and send it back" is all it takes. And
in the general case it's one line per path rather than the whole file. Neither
changes my read: silent arbitrary file read on document open, against a user who
did nothing but open a colleague's file, is a serious bug. The same applies in
jamovi cloud, where the path resolves against the server's filesystem instead.

Your escaping is correct throughout — `html_escape()` is applied at every echo
site — so this is disclosure, not injection. That's the one thing keeping it
from being worse.

**What I'd suggest:** **Remove `weightsPath` entirely.** Not "validate it", not
"restrict it to safe extensions" — an allowlist still leaves a saved document
choosing which of the victim's files gets opened, and any manual-entry path box
is a request to type in something the module will then read on someone else's
machine. Delete the option and the code will have no way to touch a path it
wasn't handed by a live user action.

The good news is that you've already built the replacement, so this mostly
subtracts code. Once the browse button is wired up (see the HIGH finding on
`jamovi/js/snpPGS.js` below), `weightsContent` covers the real use case on
desktop *and* cloud: the bytes are embedded by a deliberate in-session choice
rather than replayed from a file, and `weightsFilename` already carries the
display name — which is all `weightsPath` is actually contributing today, since
the browse handler sets it to `file.name` and `.weightsLabel()`
(`R/snpPGS.b.R:833-837`) prefers `weightsFilename` anyway. Concretely:

- Drop the option from `jamovi/snpPGS.a.yaml:92-110` and the TextBox at
  `jamovi/snpPGS.u.yaml:89-91`. Replace the TextBox with a read-only display of
  `weightsFilename`, and re-anchor the browse button — `jamovi/js/snpPGS.js:40`
  currently finds its insertion point via `ui.weightsPath`, so that needs a new
  target.
- Delete the `readLines()` fallback in `.weightsRawLines()`
  (`R/snpPGS.b.R:812-815`) and the `file.exists()` branch in `.hasWeights()`
  (`R/snpPGS.b.R:788-790`). `.weightsSig()` can lose its path+mtime branch at
  `R/snpPGS.b.R:825-828` too; the embedded-content branch above it already
  produces a usable key.
- Tidy up the 13 `clearWith` lists that name `weightsPath` —
  `jamovi/snpPGS.r.yaml:38`, `:103`, `:128`, `:192`, `:213`, `:249`, `:311`,
  `:382`, `:441`, `:473`, `:499`, `:530`, `:559`. Nothing breaks if you don't:
  every one of them already lists `weightsContent` too, which is the option that
  actually carries the weights source once the path is gone, so invalidation
  stays correct either way. The leftover entries would simply be dead
  references. Worth removing while you're there.
- While you're in `jamovi/js/snpPGS.js`, note that the `reader.onerror` handler
  at line 102 does `_setOpt(ui, 'weightsPath', file.path || file.name)` — that's
  the one place a genuine local filesystem path gets written into a saved
  option. It should just report the read failure.
- **Stop echoing file content on a parse failure.** "This file has no
  recognisable rsID column" plus the *expected* column names is just as useful
  to someone debugging their catalog and reveals nothing about the file.
- **Filter the SNP Weights grid to the selected SNPs**, or cap the rows shown.
  Showing every catalog row is a deliberate feature, I realise — but it's what
  turns a one-line leak into a whole-file one.

Worth doing now rather than later: this option is part of your public R syntax
(`jamovi/snpPGS.a.yaml:23` documents `weightsPath = "pgs_catalog.csv"` in the
usage example), so removing it is a breaking change — but only in the abstract,
because the module hasn't been published yet. There are no saved analyses in the
wild to break. That gets considerably more awkward after release.

One related item while you're in here: `memDecompress(bytes, "gzip")` at
`R/snpPGS.b.R:803-805` has no size cap, so a small crafted `.gz` embedded in
`weightsContent` can expand without bound in the engine process — same delivery
vector, denial of service rather than disclosure. Worth a sanity limit on the
decompressed size.

### [HIGH] Version is below the library's minimum
**File:** `DESCRIPTION:4`, `jamovi/0000.yaml:4`
**Pattern:** `Version: 0.5.0`

**Why this matters:** The library's minimum accepted version is `0.8.0`, so at
`0.5.0` this module can't be published as it stands. That's the mechanical
part, and it's a one-line fix. The part I'd actually press you on is what the
number is saying: a `0.x` version tells everyone who finds your module that its
own author doesn't consider it finished yet, and people read it exactly that
way. Having now read the whole thing, I don't think that's the message you want
to be sending — the schema is flawless, the `clearWith` coverage is complete,
and there's a 2,300-line test suite with golden values behind it. The version
number is undershooting the work by a wide margin.

**What I'd suggest:** Go to `1.0.0`, not `0.8.0`, in both `DESCRIPTION` and
`jamovi/0000.yaml` (they must match exactly). Clearing the bar by the bare
minimum would leave you at `0.8.x`, which is publishable but still reads as
provisional — and by everything I can see here, this module isn't provisional.
I'd make the change last, after the other fixes below, so the 1.0 tag lands on
a clean tree.

### [HIGH] `ggplot2` and `base64enc` are used but not declared as dependencies
**File:** `DESCRIPTION:14-18`
**Pattern:** `Imports: jmvcore (>= 1.2.0), R6, nnet`

**Why this matters:** `ggplot2` is called via `::` in 79 places
(`R/snpPGS_plots.R` throughout, plus `R/snpStats.b.R:1831-1849`) and
`base64enc::base64decode` at `R/snpPGS.b.R:800`, but neither appears in
`Imports:` or `Depends:`, and neither has an `importFrom()` in `NAMESPACE`. The
comment at `R/snpPGS.b.R:795-796` names the reason it works today —
*"base64enc + jsonlite are jmvcore imports, so base64enc::base64decode is
always available at runtime"*. That's true right now, and it's exactly the
fragility I'd want flagged: R's dependency resolution only guarantees what is
listed in `Imports:`. Nothing pins jmvcore to keep depending on `base64enc`, or
`ggplot2` to stay in the environment. The day an upstream release drops either,
every plot in your module and the entire cloud weights-file path stop working —
with an error that points at your code, not at the real cause.

**What I'd suggest:** Add both to `Imports:` in `DESCRIPTION`. `ggplot2` is
heavily used so an `Imports:` entry alone is right (keep calling it via `::`);
for `base64enc` a single `importFrom(base64enc, base64decode)` in `NAMESPACE`
alongside the `Imports:` entry would also be reasonable.

### [HIGH] The weights file-browse button is almost certainly never wired up
**File:** `jamovi/js/snpPGS.events.js:5`, `jamovi/js/snpPGS.js:3-13`
**Pattern:** `const events = {};` — while the real handlers live in a different file

**Why this matters:** `jamovi/js/snpPGS.events.js` exports an empty `events`
object. Your actual `view_updated` / `view_loaded` handlers — the ones that
inject the 📁 browse button and embed the chosen file into `weightsContent` —
are in `jamovi/js/snpPGS.js`, which nothing references: `jamovi/snpPGS.u.yaml`
has no `events:` block, so jamovi auto-loads `<name>.events.js` and finds
nothing to do. The consequence is significant, because a lot of design work
depends on this file: without the button, `weightsContent` and
`weightsFilename` are never set, so the only way to supply weights is to type a
path into the `weightsPath` TextBox — which, as your own option description at
`jamovi/snpPGS.a.yaml:99-110` explains, cannot work in jamovi cloud, since the
browser's path doesn't exist on the server running R. So the whole
cloud-compatible path you carefully built is dark.

**What I'd suggest:** Move the contents of `jamovi/js/snpPGS.js` into
`jamovi/js/snpPGS.events.js` (exporting `view_updated` and `view_loaded` on the
`events` object), or keep the file where it is and declare it explicitly in
`jamovi/snpPGS.u.yaml` with an `events:` block pointing at `./snpPGS`. Then
install into a clean jamovi and confirm the button actually appears next to the
weights TextBox — this is worth verifying by hand rather than by inspection.

### [MEDIUM] Haplotype interaction tables build their columns in `.run()`
**File:** `R/snpStats.b.R:2271`, `R/snpStats.b.R:2313`, `R/snpStats.b.R:2342-2345`
**Pattern:** `tbl_cross$addColumn(name = col_nm, title = paste0(lvl, ...), type = "text")`

**Why this matters:** You already documented exactly why this is a problem — at
`R/snpStats.b.R:283-285`: *"addColumn in .run has the same defect as addRow — a
column absent at restore never gets its cells back, so the stratified columns
blanked on every click."* The three haplotype interaction tables
(`haploInteractionTable`, `haploCondCovarTable`, `haploCondHaploTable`) get
their columns added only inside `.compute_haplo_interaction()`, and unlike
`covDescTable` and the SNP interaction tables they get no pre-seeding in
`.init()`. Those columns are the levels of the interaction covariate, which
`.init()` can already determine — it reads the same data for `.strat_levels()`
at `R/snpStats.b.R:313`. So users running a haplotype interaction will see those
three tables blank out on every unrelated option click, which is the exact
behaviour the rest of the module goes to real lengths to avoid.

**What I'd suggest:** In `.init()`, when `haploInteraction` is on and a
categorical first covariate is available, pre-create the per-level columns on
all three tables the same way you do for `covDescTable` at
`R/snpStats.b.R:279-289`. The *rows* genuinely can't be known until `haplo.em`
has run, so leaving those in `.run()` is correct — it's only the columns that
are predictable.


### [MEDIUM] `genetics` is a `Depends:` and you've flagged it as obsolete yourself
**File:** `DESCRIPTION:14`
**Pattern:** `Depends: genetics, haplo.stats`

**Why this matters:** Your own `NEWS.md` plan says *"remove genetics dependency
because package is marked obsolete"*, and I agree that's the right call to
prioritise. jamovi resolves module dependencies from a pinned package snapshot;
if a deprecated package stops being carried in that snapshot, the module won't
install at all — not a degraded feature, a hard failure. `genetics::genotype`,
`genetics::allele`, `genetics::HWE.exact` and `genetics::LD` are used in 34
places across `R/snpStats.b.R` and `R/snp_compute.R`, so this isn't a small
change, but it's the single biggest risk to the module's long-term
availability. Separately, `Depends:` attaches both packages to the user's
search path when your namespace loads, which is stronger than you need — your
code already calls everything through `::` and `importFrom()`.

**What I'd suggest:** Move `genetics` and `haplo.stats` from `Depends:` to
`Imports:` now (a one-line change with no code impact, since the `::` calls and
`NAMESPACE` `importFrom()` lines already exist). Then plan the `genetics`
removal properly — HWE exact tests and pairwise LD are both implementable
directly, and it would leave `haplo.stats` as your only specialist genetics
dependency.

### [MEDIUM] Status messages are hand-styled HTML with hardcoded colours
**File:** `R/snpStats.b.R:455`, `R/snpStats.b.R:547`, `R/snpPGS.b.R:688`, and 15 more
**Pattern:** `"<p style='color:orange;'>Haplotype association and interaction analyses are only implemented for binary and quantitative responses.</p>"`

**Why this matters:** There are 18 sites across `R/snpStats.b.R`,
`R/snpPGS.b.R` and `R/snp_compute.R:364` that write validation and status
messages as `Html` content with a literal colour — `red`, `orange`, `#c0392b`,
`#555`, `#666`. Two problems. First, those colours are fixed against a light
background; in jamovi's dark theme `#555` and `#666` on dark grey are close to
unreadable. Second, jamovi has a purpose-built result type for exactly this —
`type: Notice` in `.r.yaml`, populated with `setContent()` — which renders with
the platform's own warning/info styling, adapts to the theme automatically, and
looks consistent with every other module the user has installed.

**What I'd suggest:** Convert `validationMsg` and `haploNotImplMsg` (and the
PGS equivalents) from `type: Html` to `type: Notice` in both `.r.yaml` files,
and drop the inline `<p style='...'>` wrappers — pass the plain message text.
The `helpBanner` at `R/snpStats.b.R:255-258` is a different case and fine to
leave as `Html`, though I'd drop the `color:#666` there too and let jamovi pick
the text colour.

### [LOW] `.init()` reads the full dataset up to six times per option click
**File:** `R/snpStats.b.R:41-46`, called at `:272`, `:313`, `:330`, `:383`, `:404`, `:433`
**Pattern:** `tryCatch(self$readDataset(FALSE), error = function(e) d)`

**Why this matters:** Your comment is honest about the trade-off — reading
values in `.init()` buys an exact row-structure prediction *"at the cost of one
dataset read per option click"*. But it's not one read: `.init_data()` is called
six separate times within a single `.init()`, and each call re-reads. For the
datasets you ship that's fine; for the GWAS-scale data this module is aimed at
(your own `CRCgenet-SNPs.tsv` has 65 SNPs across 2,837 rows, and real users will
bring far more), six full reads on every checkbox click will make the options
panel feel sluggish.

**What I'd suggest:** Memoise it — cache the result in a private field on first
call within `.init()` and return the cached frame thereafter, invalidating on
the same signature you already build for `.prep_key` at `R/snpStats.b.R:495-502`.
That's a small change that turns six reads into one.

### [LOW] Checkbox labels start with "Show"
**File:** `jamovi/snpStats.a.yaml:118`, `:123`, `:198`, `:203`, `:218`
**Pattern:** `title: Show SNP missingness plot`

**Why this matters:** jamovi's convention is that a checkbox label names the
*thing*, not the action — "SNP missingness plot", not "Show SNP missingness
plot". The checkbox itself already communicates "show/don't show", so the verb
is redundant and makes the option list read as a series of commands rather than
a list of available output. Worth noting you clearly know this already: the PGS
UI overrides these labels correctly (`jamovi/snpPGS.u.yaml:35` renders
`showSnpGrid` as "SNP weights table", not "Show SNP weights table"). It's only
the SNP Analysis panel, which has no `label:` overrides, where the `.a.yaml`
titles surface as-is.

**What I'd suggest:** Reword the five titles in `jamovi/snpStats.a.yaml` —
"Missing values in tables", "SNP missingness plot", "Interaction table",
"Adjustment covariate parameters", "Cross-classification table". I'd also
soften `:73` ("Stratify by response groups" → "Stratified by response groups")
and `:83` ("Remove missing values in SNPs" → "SNPs with missing values
removed"), though those are more marginal. The `Show …` titles in
`jamovi/snpPGS.a.yaml` are fine to leave since the UI overrides them, but
aligning them would keep the generated R documentation consistent too.

### [LOW] The missingness plot renders from a private field rather than image state
**File:** `R/snpStats.b.R:1612-1613`
**Pattern:** `cache <- private$.miss_cache` / `if (is.null(cache) || length(cache) == 0) return(FALSE)`

**Why this matters:** `.render_ld_plot` at `R/snpStats.b.R:1788-1789` does this
the right way — it reads `image$state`, which was populated by
`item$ldPlotImage$setState(...)` at `:1783`, and is guarded against `NULL`.
`.plotMissingness` instead reads `private$.miss_cache`, a plain R6 field. As
your own comments elsewhere note, jamovi rebuilds the analysis object on every
option click, so that field doesn't survive; if jamovi ever redraws the image
without having re-run `.run()`, the plot silently returns `FALSE` and the user
gets a blank panel. The guard means it fails safely rather than erroring, which
is good, but blank isn't the intended outcome.

**What I'd suggest:** Call `setState()` on the missingness image in
`.run_descriptive()` with the per-SNP percentages, and read `image$state` in
`.plotMissingness` — the same pattern as `.render_ld_plot`. The cached object
here is tiny (one percentage per SNP), so there's no file-size downside. The
five PGS plots at `R/snpPGS.b.R:2907-2911` use `private$.cache` the same way,
but there the cached object includes the dosage matrix, and serialising *that*
into the saved file would cost far more than the occasional recompute — I'd
leave those alone. It's really just the missingness plot where state is a clear
win.

### [INFO] No strings are marked for translation

**Why this matters:** Every user-facing string — table titles, notes,

### [INFO] `References:` is not a recognised `DESCRIPTION` field
**File:** `DESCRIPTION:21-22`
**Pattern:** `References:` … `<em>Bioinformatics</em> 22(15):1928–1929.`

**Why this matters:** `References:` isn't a field R knows about, so nothing
reads it — and `R CMD check` will emit a note about the unknown field. It also
contains HTML markup (`<em>`) and a non-ASCII en dash, neither of which belong
in `DESCRIPTION`. The good news is that this citation is already properly
handled where it counts: `jamovi/00refs.yaml` has it under the `bioinfo` key
with a title, author, year and DOI URL, and both `.r.yaml` files reference it,
so jamovi shows the citation in the results.

**What I'd suggest:** Delete the `References:` field. If you want the citation
discoverable from the package metadata, add a `CITATION` file under `inst/`
instead — that's the standard mechanism and `citation("SNPstats")` will pick it
up.
